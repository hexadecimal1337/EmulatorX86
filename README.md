# EmulatorX86

Небольшой учебный эмулятор x86 с GUI на ImGui + DirectX 11. Проект собирается как Visual Studio solution и состоит из трех основных частей: память/контекст процессора, декодер и исполнитель инструкций, графическая оболочка.

## Что есть сейчас

- GUI на ImGui с окнами процессора, памяти и простого ассемблера.
- Контекст потока с регистрами `EAX..EDI`, `EIP`, `EFLAGS`, частотой и счетчиком тактов.
- Пейджинговая модель памяти `0x1000` на страницу.
- Отдельный поток исполнения в `EmulatorManager`.
- Базовый набор инструкций:
  - `mov`
  - `or`
  - `and`
  - `xor`
  - `cmp`
  - `jb`, `jnb`, `je`, `jne`, `jbe`, `ja`
  - `sub`
  - `add`
  - `test`
  - `int3`
  - `jmp`
  - `push`
  - `pop`

## Структура проекта

- `src/Main.cpp` - запуск менеджеров памяти, эмуляции и GUI.
- `src/Logic/MemoryManager.*` - эмулируемая память и контекст CPU.
- `src/Logic/InstructionManager.*` - парсер asm, декодирование и выполнение инструкций.
- `src/Logic/EmulatorManager.*` - поток исполнения, run/stop/single-step.
- `src/Gui/GUI.*` - окна интерфейса и кнопки управления.
- `src/Gui/GraphicsManager.*` - окно, DirectX 11 и инициализация ImGui.

## Как это работает сейчас

1. `Main.cpp` инициализирует память, GUI и поток эмулятора.
2. `EmulatorManager::workFunction()` постоянно крутится в фоне.
3. Когда выполнение разрешено, вызывается `InstructionManager::decodeInstruction()`.
4. После задержки по тактам вызывается `InstructionManager::processInstruction()`.
5. Остановка происходит по кнопке, по ошибке, по `int3` или после одиночного шага.

## Сильные стороны текущей реализации

- Код разделен по ролям: GUI, логика эмуляции, память.
- Для учебного проекта ISA оформлена достаточно прямо: декодирование и исполнение читаются без лишней абстракции.
- Ассемблер, редактор и просмотр памяти уже встроены, поэтому удобно отлаживать новые инструкции.
- `InstructionData` уже хранит все, что нужно для отладочных режимов: адрес, размер и такты инструкции.

## Что мешает дальше развивать отладчик

- В `EmulatorManager` пока только два режима: непрерывный запуск и одиночный шаг.
- В ISA нет `call` и `ret`, поэтому полноценный `step over` пока реализовать нечем.
- Логика одного шага размазана по `workFunction()`, из-за чего новые режимы остановки будет неудобно добавлять прямо в текущий цикл.
- В проекте есть дублирование имен файлов `SettingManager.*` и пустой `SettingsManager.cpp`, это не ломает архитектуру, но добавляет шум.

## Как лучше добавить Step Into и Step Over

### Короткий вывод

Лучший путь: сначала выделить единый примитив "выполнить одну инструкцию", потом добавить `call/ret`, и только после этого вводить режимы `step into` и `step over` через явные stop-condition.

### 1. Нормализовать режимы выполнения в EmulatorManager

Вместо набора флагов лучше ввести явный режим выполнения, например:

```cpp
enum class RunMode {
    Stopped,
    Running,
    StepInto,
    StepOver,
    StepOut
};

struct StopCondition {
    bool active = false;
    DWORD targetEip = 0;
    DWORD targetEsp = 0;
};
```

Идея простая:

- `StepInto` = выполнить ровно одну инструкцию и остановиться.
- `StepOver` = если текущая инструкция не `call`, это тот же `StepInto`.
- `StepOver` для `call` = выполнить вызов и бежать дальше, пока не вернемся на адрес следующей инструкции.

### 2. Вытащить из workFunction один атомарный шаг

Сейчас в `workFunction()` смешаны:

- ожидание;
- декодирование;
- задержка по тактам;
- выполнение;
- принятие решения об остановке.

Лучше вынести это в отдельный метод, например:

```cpp
StepStatus EmulatorManager::executeOneInstruction(InstructionData* lastInstruction);
```

Тогда главный цикл станет простым:

- ждать, пока режим не `Stopped`;
- выполнить одну инструкцию;
- проверить stop-condition;
- решить, продолжать или останавливаться.

Это самый важный рефакторинг перед `step over`.

### 3. Добавить call/ret как минимально необходимую основу

Для `step over` нужен реальный вызов функции. Минимальный объем:

- `call <addr>`
- `call <label>`
- `ret`

Проще всего сначала сделать `call` по той же модели, что и `jmp`:

- декодирование операнда аналогично `jmp`;
- перед переходом в стек кладется адрес возврата `currentEip + instSize`;
- затем `EIP` меняется на адрес назначения;
- у `ret` адрес читается со стека и загружается в `EIP`.

С учетом текущей модели стека в проекте (`push` пишет по `ESP`, потом уменьшает `ESP`) `call/ret` надо делать в той же внутренней конвенции, иначе поведение сломается.

### 4. Реализовать Step Over через временное условие остановки

Рекомендуемая логика:

1. Декодировать текущую инструкцию без выполнения.
2. Если это не `call`, выполнить обычный `StepInto`.
3. Если это `call`, вычислить:
   - `returnAddress = currentEip + instSize`
   - `initialEsp = currentEsp`
4. Запустить режим `Running` с временным условием остановки:
   - остановиться, когда `EIP == returnAddress` и `ESP == initialEsp`
   - также останавливаться по ошибке, `int3` и ручному `stop`

Почему так лучше, чем просто ждать `EIP == returnAddress`:

- проверка `ESP` страхует от ложного совпадения адреса;
- схема не требует полноценного call stack объекта;
- реализация остается маленькой и хорошо ложится на текущую архитектуру.

### 5. Step Out лучше делать вторым этапом

Если позже понадобится `step out`, его уже удобно строить поверх той же схемы:

- запомнить `initialEsp`;
- продолжать выполнение, пока `ESP` не станет больше или равно ожидаемому уровню возврата;
- дополнительно останавливать по `ret`, ошибке или breakpoint.

Но сначала достаточно качественно закрыть `step into` и `step over`.

## Рекомендуемый порядок изменений

1. Вынести `executeOneInstruction()` из `EmulatorManager::workFunction()`.
2. Ввести `RunMode` и `StopCondition` вместо `stepFlag`.
3. Добавить опкоды `CALL` и `RET` в `Structs.h`.
4. Добавить `decodeCALL/processCALL` и `decodeRET/processRET` в `InstructionManager`.
5. Подключить `makeStepOver()` в `EmulatorManager`.
6. Привязать кнопку `"Шаг с обходом"` в GUI.
7. Уже после этого, если нужно, добавлять `step out`.

## Практическая рекомендация

Если цель на ближайший шаг - получить рабочий отладочный UX без большого рефакторинга, то делай так:

1. Оставь текущий `makeStepIn()` как `Step Into`.
2. Реализуй только `call` и `ret`.
3. Добавь `makeStepOver()` через временный `targetEip + targetEsp`.
4. `step out` пока не трогай.

Это даст максимум результата за минимальный объем кода.
